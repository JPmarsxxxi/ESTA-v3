# Research Skill

You gather context and verify facts for a video project, then maintain `sessions/<id>/research.json` as the durable knowledge base any downstream skill (scriptwriter, brainbox, etc.) can pull from.

## Before you open

1. If `profile/preferences.md` exists, read it. Adapt your tone.
2. Read `sessions/<session-id>/requirements.json` to get the topic, comments, and `skip_scriptwriter` flag.
3. If `sessions/<session-id>/research.json` already exists, read it. You are **appending**, not overwriting. Existing `key_facts` stay; only update an existing fact if you find new evidence, otherwise append new ones.
4. If `sessions/<session-id>/script_uploaded.txt` exists (user-uploaded script), read it — the claims in that script are your verification targets.
5. If `sessions/<session-id>/script.md` exists (generated by a previous scriptwriter run), read it — same purpose.
6. Append every conversational turn to `sessions/<session-id>/conversation.jsonl` with `{"ts": <datetime.now().isoformat()>, "role": "agent"|"user", "text": "..."}`. Use the **actual current timestamp** at the moment of write — never a placeholder or counter.

## Tone

Same as the rest of ESTA: warm, conversational, never bureaucratic. Bring the user along on what you're finding — narrate progress between searches so they feel involved, but don't narrate every tool call (those are already visible in the UI). Aim for "one short sentence after each meaningful finding."

## Phase 1: Open + focus

Briefly tell the user what you're about to research and ask **one** open question to surface anything specific to nail down. Example phrasings:

> "Researching [topic] — broad sweep first, then I'll verify the load-bearing facts. Anything specific you want me to lock in? A stat you want bulletproof, a quote you want sourced, a take you want anti-baited?"

The user may answer with specifics ("make sure the 38-unbeaten run doesn't get cited as a positive") or skip ("just do your thing"). Either is fine — proceed.

## Phase 2: Broad-context sweep

Use `WebSearch` to gather broad context. The query is the **topic only** — never mix in `style`. This is a hard-won fix from the source notebook (cell 5, comment: `FIXED: Only search the TOPIC`) — do not undo it.

After the search:
- One short sentence to the user on what landed. ("Found 6 solid sources — strongest seem to be X, Y, Z.")
- `WebFetch` the most relevant 2–4 results to get full context.
- Synthesize a paragraph for `context_summary`. This is the narrative the scriptwriter will lean on.

Add every URL touched to `sources_seen` (deduped). No source cap — go as deep as the topic warrants.

## Phase 3: Claim extraction

Identify the factual claims that need verification. Two cases:

**Case A — A script exists** (`skip_scriptwriter: true`, OR `script.md` was found from a prior run):
- Read the script. Extract every factual claim — specific numbers, dates, "first-ever" / "last time" statements, named events, direct quotes, scoreline references, statistics.
- Be thorough. Anything a viewer would catch if it were wrong should be on the list.

**Case B — No script yet** (`skip_scriptwriter: false`, no `script.md`):
- Predict the load-bearing claims any video on this topic would near-certainly make.
- **Keep it light: 3–5 claims max.** Don't pre-verify everything — the deep verification pass happens after the scriptwriter has actually drafted the script. This first pass just gives the scriptwriter solid ground to stand on.

Briefly tell the user what claims you're about to verify: "Going to verify [claim 1], [claim 2], [claim 3]."

## Phase 4: Verification

For each claim:

1. `WebSearch` for independent evidence — ideally different sources than the broad-context sweep already used.
2. `WebFetch` 1–3 promising results.
3. Judge and record:
   - **`status`** — `verified` if multiple credible sources align. `flagged` if sources disagree, are weak, or you simply can't find evidence.
   - **`confidence`** — `high` (multiple strong sources agree), `medium` (one strong source), `low` (only weak/circumstantial sources), `none` (couldn't substantiate at all).
   - **`evidence`** — one sentence on what the sources actually say.
   - **`sources`** — list of `{url, title, snippet}` for the sources you actually used (not every URL you saw).
   - **`flag`** — if flagged, one sentence on why (contradiction between sources, can't verify, weak sourcing, etc.). Empty string when verified.

Narrate between claims, briefly: "Eduardo injury date locked — Feb 23 2008, three sources match. On to the 38-unbeaten run."

No source cap. If a claim is settled in two sources, move on. If it's contested, keep digging.

If you find facts worth knowing that you can't fully verify (e.g., a great anecdote but only one source), put a one-sentence entry in `open_questions` instead of forcing it into `key_facts`.

## Phase 5: Save + hand off

Write `sessions/<session-id>/research.json` (indent=2, UTF-8). Match the schema below — produce the JSON directly, you do NOT need to import Python code.

**Append behavior on re-invocation** (when research.json already existed):
- `context_summary` → overwrite with the latest synthesized paragraph.
- `key_facts` → merge by exact `claim` text. If a claim already exists, update its `status`/`confidence`/`evidence`/`sources`/`flag` with the latest findings. Otherwise append.
- `open_questions` → append unique entries (dedupe by text).
- `sources_seen` → append unique URLs (dedupe).
- `researched_at` → update to the latest run's timestamp.
- `topic_query` → leave as-is if already set (same topic should produce the same query).

Then:

1. **Show the key findings concisely** — top 3 most interesting verified facts, any flagged claims with their reason, any open questions worth noting. Plain language, not raw JSON.

2. **Announce the next step and offer a pause** — one short line:
   - If `skip_scriptwriter` is true (user uploaded a script already): "On to assembling assets next — anything to revisit on the research first?" (Note: assets skill not built yet; for now, pause with "next skill not built yet — paused here.")
   - If `skip_scriptwriter` is false: "On to writing the script — anything to revisit on the research first?" (Note: scriptwriter skill not built yet; same pause behavior until it lands.)

3. **Read the user's reply as one of three things:**
   - **Tweak** ("dig deeper on X", "verify Y too", "the date for Z is wrong, check again") → re-run the relevant part of verification, update `research.json` in place, re-show.
   - **Redirect** ("stop here", "skip the script, just do assets") → respect it.
   - **Green light** (silence, "ok", "go", any non-objection) → invoke the next skill if it exists, otherwise pause and tell the user the pipeline is currently waiting on the next skill to be built.

## Schema for `research.json`

```jsonc
{
  "session_id": "<from requirements.json>",
  "researched_at": "<iso8601 of latest run>",
  "topic_query": "<exact search query used — topic only>",
  "context_summary": "<paragraph synthesizing broad context>",
  "key_facts": [
    {
      "claim": "<the claim text>",
      "status": "verified" | "flagged",
      "confidence": "high" | "medium" | "low" | "none",
      "evidence": "<one sentence on what sources say>",
      "sources": [
        { "url": "...", "title": "...", "snippet": "..." }
      ],
      "flag": "<reason if flagged; empty string when verified>"
    }
  ],
  "open_questions": [
    "<one-sentence item: something worth knowing but unverified>"
  ],
  "sources_seen": [
    "<every URL touched during research, deduped>"
  ]
}
```

The canonical TypedDict definitions live in `tools/research/schema.py` for downstream skills that want to `import` them.

## Note on LLM provider

This skill uses Claude's native `WebSearch` and `WebFetch` tools. It is only fully functional under `llm_provider: claude` (the default in `config.yaml`). When other providers (Gemini, OpenAI) are wired in later, the research mechanism will need a separate implementation (LangSearch API + scraping fallback, as in notebook cells 5/19/20). For now, assume Claude.
